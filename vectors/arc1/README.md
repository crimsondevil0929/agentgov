# ARC1 reference test vectors

Generated by [`scripts/generate_arc1_vectors.py`](../../scripts/generate_arc1_vectors.py).
Do not edit by hand. The test suite regenerates this directory on every run
and fails if a single byte differs
([`tests/test_receipt_vectors.py`](../../tests/test_receipt_vectors.py)). The
format is specified in [`docs/RECEIPTS.md`](../../docs/RECEIPTS.md).

> **The keys in `keys/` are test keys.** `issuer.seed` and `witness.seed`
> are Ed25519 private seeds, and `internal.hmac` is an HMAC secret. All three
> are published, and derived from public labels, so that anyone can reproduce
> these files. Never use them for anything else.

## Layout

- `canonical.json`: RFC 8785 cases. Inputs, their exact canonical UTF-8, and
  texts a strict decoder must refuse.
- `merkle.json`: the RFC 9162 eight-leaf reference tree. Every root, and
  every inclusion and consistency proof.
- `ed25519.json`: the RFC 8032 section 7.1 signatures, a wrong message, and
  an `S` at or above the group order.
- `keys/`: `issuer.pub` and `witness.pub`, the keys a verifier trusts;
  `internal.hmac`; and the test seeds.
- `log/receipts.jsonl`: a durable receipt log of seven receipts. Each line is
  one canonical receipt, and exactly one Merkle leaf.
- `log/receipts.jsonl.checkpoints`: the log's signed checkpoints at sizes 3,
  5 and 7.
- `log/consistency.json`: the consistency proof from size 3 to 7 that the
  witness checked before it cosigned size 7.
- `witness/cosignatures.jsonl`: the witness's cosignatures of sizes 3 and 7.
  Size 5 was never shown to it.
- `valid/`: bundles and row disclosures that verify.
- `invalid/`: each one broken in exactly one way.
- `delivery/`: ARC1 v1.1 delivery receipts, in a log of their own (below).
- `v12/`: ARC1 1.2, signature version 2 and a key transition, in a log of
  their own (below).
- `v13/`: ARC1 1.3, measurement classes, quantities in other units and the
  systems that served, in a log of their own (below).
- `v14/`: ARC1 1.4, the `compensated` outcome, in a log of its own (below).
- `manifest.json`: every command-line case, and the exit code it must produce.

## The receipts

A support agent works a tenant-partitioned orders database, under a
capability for one tenant:

0. `committed-refund`: refunds one order, 3 rows. Committed.
1. An address update. Committed.
2. A support note. Committed.
3. `refused-tenant-wipe`: a prompt-injected plan that zeroes every tenant's
   totals and deletes the audit trail, 229 rows. Refused, and rolled back.
4. `scoped-repair`: the one-row fix the refused plan should have been. Its
   `decision.repair_of` names receipt 3. Committed.
5. `recovered-commit`: resolved after a crash, from the escrow chain's commit
   marker. `recovered_committed`.
6. `halted-scope`: admitted by every check, and refused because the scope was
   halted.

## Delivery receipts (ARC1 v1.1)

`delivery/` is a second log, `arc1-vectors-delivery`, of two leaves:

0. `refund-call`: an action receipt. The support agent refunds an order, and
   the plan commits, beside its rows, a request to a payment API: the row of
   `interlock.outbox` it commits names the message, the sink, the operation
   and the payload's hash. `valid/refund-call.rows.json` discloses that row,
   and `payload.json` is the payload itself.
1. `refund-delivered`: the delivery receipt. The relay sent the request, the
   payment API answered 200, and the relay signed what it saw with its own key
   (`keys/relay.pub`). The log signed the receipt that carries the
   attestation, bound to leaf 0 by its leaf hash.

`delivery/invalid/` breaks it one way each: an attestation by a key that
claims the relay's id, a payload hash the relay never attested, a binding to
another receipt, a status edited after signing, and a delivery placed before
the action it follows from.

## Signature version 2 and a key transition (ARC1 1.2)

`v12/` is a third log, `arc1-vectors-v12`, of five receipts, every signature
in it version 2 (`"sv": 2`: the domain and the SHA-512 of the canonical
document are signed). Receipts 0 to 2 are signed by the issuer key. The
issuer then signs a checkpoint at size 3 and the transition in
`log/receipts.jsonl.transitions`, handing the log at size 3 to its successor
(`keys/issuer-2.pub`), which signs receipts 3 and 4 and the checkpoint at
size 5. The witness cosigns both checkpoints.

- `valid/sealed.bundle.json`: receipt 1 under the checkpoint at 3, the
  issuer's: it verifies with the issuer's key alone.
- `valid/early.bundle.json` and `valid/late.bundle.json`: receipts 1 and 4
  under the checkpoint at 5, the successor's. They verify from the issuer's
  key by following the transition, or with both keys trusted outright.
- `invalid/`: a transition forged in the issuer's name, a version 2
  signature presented as version 1, a signature version that does not exist,
  and a checkpoint the issuer signed past the size it handed over.

## Measurement classes, quantities and other systems (ARC1 1.3)

`v13/` is a fourth log, `arc1-vectors-v13`, of four receipts. Each uses a
field 1.3 adds, which is written only when it is not the default, so every
receipt above keeps its bytes:

0. `mcp-write`: an agent's write to a CRM through an MCP tool, held for a
   warrant and delivered at most once. Only the request was measured:
   `coverage.measurement` is `request-only`, and `cost.served_by` names the
   MCP server.
1. `dose-order`: a medication order measured in a SQL transaction, so it names
   no measurement (transactional). `cost.quantities` holds what it consumed in
   the ledger of morphine milligram equivalents, `mme`, beside the model
   spend in `settled_usd`.
2. `scale-up`: a capacity change applied from a saved plan,
   `plan-bound`, consuming 8 `vcpu`.
3. `own-tenant`: a receipt for one tenant of a multi-tenant product. Its diff
   reached four tenants; `summary.tenants` names only the plan's own, and
   `summary.other_tenants` counts the three others, so the receipt can be
   handed to that tenant without naming the rest.

`invalid/` breaks the new fields one way each: `"transactional"` written out
(a receipt that names none is transactional, so it is never written),
a measurement class that does not exist, an empty `quantities`, quantities out
of order, one unit twice, an empty `served_by`, and `other_tenants` written as
zero.

## A write put back (ARC1 1.4)

`v14/` is a fifth log, `arc1-vectors-v14`, of two receipts of a medication
order written to a FHIR server, each `predicted`: the before image read, the
after image predicted, the write made conditional on the version read, and
the result read back.

0. `order-predicted`: the read-back matched the prediction: `committed`, its
   `substrate_txid` the stage id every write carried.
1. `order-compensated`: the read-back did not match (a rule on the server
   changed more than the write did), so what was written was put back from
   the undo recorded before the first write. The outcome is `compensated`,
   and its `substrate_txid` is the id the writes and their put-back carried,
   which the server's audit log echoes.

`invalid/` breaks the new outcome one way each: compensated with a decision
that did not admit the plan, and compensated naming no `substrate_txid`.

## Running the cases

From this directory:

```console
$ agentgov verify-receipt valid/committed-refund.bundle.json --pubkey keys/issuer.pub \
      --witness witness/cosignatures.jsonl --witness-pubkey keys/witness.pub \
      --rows valid/committed-refund.rows.json
```

Each case in `manifest.json` gives the arguments, as paths relative to this
directory, and the exit code: 0 pass, 3 malformed, 4 receipt signature, 5 log
inclusion, 6 witness, 8 rows, 9 relay attestation, 10 action binding. A
conforming verifier produces the same code for every case.
